MCP is used to connect external tools into Cebian. Once an MCP server is configured, the tools it provides appear in the Agent's tool list, and the model can call them on demand during a conversation.

It's a good fit for connecting databases, internal systems, file services, business APIs, or any tool already packaged as an MCP server.

![Screenshot](./snapshot.png)

## Add an MCP server

The entry point is under "Settings → MCP servers".

After clicking "Add MCP server", you need to fill in:

- Name: to help you tell them apart in the list, such as `github`, `weather`, or `my-tools`
- Transport: `streamable-http` or `sse`
- URL: the HTTP address of the MCP server
- Authentication: none, or Bearer Token
- Custom headers: fill in when you need extra request headers

After saving and enabling a server, the settings page queries its status and starts a background connection / tool-discovery attempt if needed, without requiring a conversation. Status refreshes about every 5 seconds. Saving the configuration does not mean the connection succeeded.

## Choosing a transport

If your MCP server supports `streamable-http`, prefer it.

`sse` is mainly for compatibility with some older services. Both require an HTTP or HTTPS address; you can't enter a local file path or other protocols.

## Use it in a conversation

After configuring and enabling a server, you don't need to manually copy tool names.

When your question requires an external tool, the Agent decides on its own whether to call an MCP tool. For example, if you connected a weather-lookup server, you can simply ask:

```md
Look up tomorrow's weather in Shanghai for me.
```

If the server provides an MCP App with a UI, the tool result may also include an embedded interactive view. This view is provided by the corresponding server; Cebian is responsible for displaying it in the conversation.

The server card shows the most recent connection or request failure; a successful request clears it. Failed background attempts wait at least 30 seconds before retrying, rather than reconnecting at every status refresh. Repeated failures also trigger a short circuit-breaker cooldown. Changing the URL, transport, authentication, or headers, or disabling and re-enabling a server, resets its connection and tool cache.

If a service isn't needed for now, you can disable it instead of deleting the configuration.

## Authentication and headers

If the server requires a Bearer Token, select Bearer Token under "Authentication" and enter the token.

If the server requires other request headers, add them under "Custom headers". Note: when using a Bearer Token, don't manually add an `Authorization` header again; Cebian handles it automatically.

## Troubleshooting connections and tool calls

- **Start with the card's error**: check the full MCP endpoint path, transport, network, token, and headers. A regular website URL is not necessarily an MCP endpoint. Check server logs for permission or authentication requirements.
- **Disconnected or temporarily unavailable**: save corrected settings and wait for the next status refresh. For transient failures, let the cooldown finish instead of retrying repeatedly.
- **Connected but no tool call**: confirm the server is enabled, actually exposes tools, and the selected model supports tool calling. Turning off "Tool calling" for a custom model also disables MCP use. The Agent still decides whether the task needs a tool.
- **Tool call fails**: inspect the failure details in the conversation. Argument or business errors differ from connection failures. Server-reported tool errors reach the model as failures; throttling or circuit-breaking reports a retry wait. A green dot does not mean the business operation succeeded.
- **No MCP App view**: not every tool has a UI. Failed tool calls do not create an App view. If a successful call's view fails to load, check whether the server is enabled and its UI resource can be read.
